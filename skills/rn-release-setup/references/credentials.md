# Credentials: what's needed, where they go, the rules

## Rules

- **Never open, print or copy the contents** of `.p8`, `.p12`, `.jks`/`.keystore`, service-account `.json`, `credentials.json`. Refer to them by path. `scan-credentials.sh` identifies them by name, extension and header only.
- Public files may be read: `.mobileprovision` (scanned for team, bundle id, type, expiry), `google-services.json`, `GoogleService-Info.plist` (Firebase config, not secret), and public fingerprints (SHA-1/SHA-256) of certificates.
- **Passwords** (keystore, `.p12`) are typed by the developer in their own terminal, never in the chat or a file you write.
- Non-secret identifiers can be given in the chat: App Store Connect key id, issuer id, Apple team id, keystore alias, the app's App Store Connect id.
- Credentials end up **on EAS** (encrypted, shared with the team, used by cloud and local builds). The folder the dev gave stays theirs; suggest they keep a backup in their team's password manager or vault.

## What to ask for, round by round

List only what the current round needs (SKILL.md Phases 5–7), with one line on what each is for:

**iOS** (one of):
- **App Store Connect API key** (recommended): `AuthKey_<KEYID>.p8` + Key ID + Issuer ID, plus the **Team ID**. EAS uses it to create and renew the distribution certificate and provisioning profile, and to submit to TestFlight.
- **Distribution certificate + App Store provisioning profile**: `.p12` (+ its password, typed by the dev) and `.mobileprovision`, plus the Team ID. Signs builds; submitting still needs the API key or an Apple ID login. When the dev gives both these and an API key, these are used for building and the key for submitting — EAS creates nothing in the client's team.
- **Apple ID with access to the team** (Admin or App Manager): EAS logs in interactively with 2-factor codes; works, but every new machine and CI needs the login again.

**Android**:
- **Upload keystore** — only if the app is already on Google Play: `.jks`/`.keystore` + alias (passwords typed by the dev). A new app gets one generated by EAS.
- **Google service account key** (`.json`) with release rights in Play Console — for `eas submit`.

**Push** (only if the app uses it — `push.md`): APNs key `.p8` + its key id (iOS), FCM V1 service account key + `google-services.json` (Android).

The whole list can go to the client in one message (`client-request.md`) even though the rounds upload it in order — fewer back-and-forths.

## The folder

Ask the dev to put everything in one folder and give you its path:
- **Outside the project** is best (`~/credentials/<app>/`), so nothing can be committed by accident.
- Inside the project: the scan checks git ignores each file; the inventory's `ignoreRulesMissing` must be empty first.
- Shared drive (Google Drive, OneDrive): download to the machine first, or use the drive's local sync folder path. Don't fetch from a drive yourself.

Then:

```bash
bash "<skill-dir>/scripts/scan-credentials.sh" <folder> <project-dir> --bundle-id <id> --package <name>
```

Read `files[].kind`, `details` and `problems`. Two `.p8` files, or one when the app uses push: ask which key id is which (App Store Connect API keys are listed under *Users and Access → Integrations*, APNs keys under *Certificates, Identifiers & Profiles → Keys*). A `pkcs12` can be a distribution or an APNs certificate: ask.

## Git

Make sure `.gitignore` covers these before any file arrives (add what `ignoreRulesMissing` lists):

```
# signing and store credentials
*.p8
*.p12
*.jks
*.keystore
*.mobileprovision
credentials.json
service-account*.json
```

A credential file already tracked by git: `git rm --cached <file>`, commit, and if it was ever pushed, tell the dev it must be treated as leaked — the owner revokes it and issues a new one (App Store Connect key, certificate; a leaked Android upload key needs an upload-key reset in Play Console).

## Uploading

`scripts/eas-credentials.sh` puts files on EAS by driving `eas credentials` (pinned to eas-cli 25.3.0, whose menus it knows). It never reads a credential file and stops at any password or Apple ID prompt.

| Round | Android | iOS |
|---|---|---|
| Build | `build-from-json` (keystore from `credentials.json`) | `build-from-json` (`.p12` + profile from `credentials.json`) |
| Submit | `submit-key --key <service-account.json>` | `submit-key --key <AuthKey.p8> --key-id <id> --issuer-id <id> --team-id <id>` |
| Push | `push-key --key <fcm-service-account.json>` | `push-key --key <AuthKey.p8> --key-id <id> --team-id <id>` |

**`credentials.json` for `build-from-json`** — you write it in the project root with paths and the alias (the dev gave it in the chat), and the passwords as `TYPE-IT-HERE`:

```json
{
  "android": { "keystore": { "keystorePath": "<folder>/upload.jks", "keystorePassword": "TYPE-IT-HERE", "keyAlias": "<alias>", "keyPassword": "TYPE-IT-HERE" } },
  "ios": { "provisioningProfilePath": "<folder>/<profile>.mobileprovision", "distributionCertificate": { "path": "<folder>/<cert>.p12", "password": "TYPE-IT-HERE" } }
}
```

Only the platforms being uploaded. Check git ignores it (`git check-ignore -q credentials.json`), then ask the dev to replace each `TYPE-IT-HERE` and say "done". Run `build-from-json` per platform; then `rm credentials.json` — never open it once the dev has filled it.

Credentials are stored per bundle id / package: upload once per id, with a `store` profile that builds it (usually `production`).

On Windows (Git Bash has no `expect`) or when the script exits 2, give the dev the printed `npx eas-cli@25.3.0 credentials -p …` command and the menu path from the platform reference.
