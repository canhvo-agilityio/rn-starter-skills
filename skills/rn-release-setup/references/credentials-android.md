# Android credentials

Needed for a store build: an **upload keystore** (signs the `.aab`). Needed for Google Play: an **app** in Play Console, the **first upload done by hand**, and a **service account key** for `eas submit`.

## Keystore — the decision that can't be undone

With Play App Signing (the default for apps created since 2021), Google re-signs the app with its own *app signing key*; the keystore you upload with is the *upload key*, registered with that app. An `.aab` signed with another key is rejected. Replacing a lost upload key takes a reset request in Play Console and days of waiting; for an old app without Play App Signing, a lost key means the app can never be updated.

So, **before any Android store build**:

| Situation | Do |
|---|---|
| A keystore is in the dev's folder | use it (below) |
| No keystore, and the app has **never been uploaded** to Google Play | let EAS generate one at the first build. A `--non-interactive` build generates it without asking ("✔ Created keystore", checked on eas-cli 25.3) — that's why this table comes first |
| No keystore, and the app **is already on Google Play** (or the dev isn't sure) | stop. Ask the client for the upload keystore + alias (passwords typed later by the dev), or for an upload-key reset in Play Console. Never generate a new one |

Ask the question explicitly when there's no keystore: "Is this app already on Google Play — even in internal testing?" Recommended answer only when the inventory shows no sign of a store app.

### Using a keystore from the dev

1. `credentials.json` in the project root (gitignored), paths and alias only:
   ```json
   {
     "android": {
       "keystore": {
         "keystorePath": "<folder>/upload.jks",
         "keystorePassword": "TYPE-IT-HERE",
         "keyAlias": "<alias>",
         "keyPassword": "TYPE-IT-HERE"
       }
     }
   }
   ```
2. The dev fills both passwords, then runs `npx eas-cli credentials -p android` → the `production` profile → *credentials.json: Upload/Download credentials between EAS servers and your local json* → *Upload credentials from credentials.json to EAS*.
3. The dev deletes `credentials.json` (or you `rm` it without reading).

### A keystore generated by EAS

After the first build, have the dev download a backup (`npx eas-cli credentials -p android` → *Download credentials from EAS to credentials.json*) into their team's vault, not the repo. Losing access to the EAS project shouldn't mean losing the upload key.

## Fingerprints (public)

Google Sign-In, Maps keys and Android App Links need the SHA-1 / SHA-256 of the certificates that sign the app:
- the **upload key**: from a built `.aab`, without any password — `keytool -printcert -jarfile build/app.aab`; or `eas credentials -p android`, which lists them;
- the **app signing key** (Play App Signing): Play Console → the app → *Test and release → App integrity → App signing*. Builds installed from Google Play — internal testing included — are signed with this one.

Register both where a service asks for fingerprints (`release-features.md`).

## Google Play app and first upload

1. Someone with access creates the app in Play Console (*Create app*: name, language, app or game, free or paid, declarations).
2. **The first `.aab` is uploaded by hand**: Play Console → the app → *Test and release → Testing → Internal testing* → *Create new release* → upload `build/app.aab` → save. Google's API can't make the first upload; `eas submit` works from the second build on. While the app has never been published, submits must use `releaseStatus: "draft"` (`eas.md`).
3. Internal testers: an email list on the internal testing track, and the opt-in link they open once. `rn-release` manages this; mention it in the hand-off.

## Service account for `eas submit`

The key (`.json`, `"type": "service_account"` in the scan) belongs to a Google Cloud service account that was invited in Play Console (*Users and permissions → Invite new users*, its `…@….iam.gserviceaccount.com` address) with permission to release to testing tracks for this app.

Put it on EAS — the dev runs `npx eas-cli credentials -p android` → the `production` profile → *Google Service Account* → *Upload a Google Service Account Key* → path. Then `eas.json` needs no key path (paths differ per machine).

The same kind of key can be the **FCM V1** key for push — a different service account usually. Ask which one the file is when the app uses push (`release-features.md`).

## Checking

- `npx eas-cli credentials -p android`: keystore (type, alias, SHA-1/SHA-256), service account key.
- The store build produces `build/app.aab`; `keytool -printcert -jarfile build/app.aab` shows the upload key's fingerprint, matching the one on EAS.
