# Android credentials

Menu paths below show the `production` profile: run each upload for `dev` too, since credentials live per app (`variants.md` → Credentials per app).

The Credentials page shows, under the package: **Android upload keystore** (build), **Google service account key for EAS Submit** (submit), **FCM V1 service account key** (push).

The uploads below are done with `scripts/eas-credentials.sh` (`credentials.md` → Uploading); the menu paths are what it drives, and what the dev follows by hand when it exits 2. Menu labels are eas-cli 25.3's. By hand, the dev runs commands in their own terminal (interactive menus); or the matching button on the expo.dev Credentials page. Which profile to pick: one whose bundle id / package matches the files and whose `distribution` is `store` — usually `production`; profiles sharing that id (a `staging` with the same bundle id) reuse the same credentials, so upload once per bundle id / package, not per profile. Give them the exact command, that profile, and what to choose.

## Build: upload keystore — the decision that can't be undone

With Play App Signing (the default for apps created since 2021), Google signs the app with its own *app signing key*; the keystore you upload with is the *upload key*, registered with that app. An `.aab` signed with another key is rejected. Replacing a lost upload key takes a reset request in Play Console and days of waiting; for an old app without Play App Signing, a lost key means the app can never be updated.

Decide from the dev's folder and the inventory's `releaseSigns`; ask only in the last case:

| Situation | Do |
|---|---|
| A keystore is in the folder | upload it (below) — no question |
| No keystore, `releaseSigns` empty (a new project) | EAS generates it: the dev runs `npx eas-cli credentials:configure-build -p android -e <profile>` and accepts *Generate a new Android Keystore*. (A `--non-interactive` build also generates one without asking — seen on eas-cli 25.3.) |
| No keystore, `releaseSigns` not empty | ask "Is this app already on Google Play — even in internal testing?" Yes or unsure → stop: ask the client for the upload keystore + alias, or an upload-key reset in Play Console (`client-request.md`); never generate one. No → as a new project |

### Uploading an existing keystore

1. `credentials.json` in the project root (gitignored), paths and alias only:
   ```json
   {
     "android": {
       "keystore": {
         "keystorePath": "<folder>/upload.jks",
         "keystorePassword": "TYPE-IT-HERE",
         "keyAlias": "<alias>",
         "keyPassword": "TYPE-IT-HERE"
       }
     }
   }
   ```
2. The dev fills both passwords, then runs `npx eas-cli credentials -p android` → `production` → *credentials.json: Upload/Download credentials between EAS servers and your local json* → *Upload credentials from credentials.json to EAS*.
3. The dev deletes `credentials.json` (or you `rm` it without reading).
4. Check: the SHA-1 on the Credentials page equals the **upload key certificate** SHA-1 in Play Console → the app → *Test and release → App integrity → App signing*. Different → the wrong keystore; don't continue.

### A keystore generated by EAS

Ask the dev to download a backup into their team's vault (`npx eas-cli credentials -p android` → *Download credentials from EAS to credentials.json*), not the repo.

### Fingerprints

The Credentials page shows the upload key's MD5 / SHA-1 / SHA-256 (public). Note them in the plan: Google Sign-In, Maps keys and App Links need them later, together with the **app signing key** fingerprints from Play Console (builds installed from Google Play — internal testing included — are signed with that one).

## Submit: Google service account key on EAS

`eas submit` uploads to Google Play with a Google Cloud **service account** that was invited in Play Console with permission to release to testing tracks for this app (`client-request.md`). The scan shows the file as `google-service-account`.

The dev uploads it: `npx eas-cli credentials -p android` → `production` → *Google Service Account* → *Manage your Google Service Account Key for Play Store Submissions* → *Upload a new service account key* → the path; or the *Add a Google service account key* button on the Credentials page. Then `eas.json` needs no key path.

The Credentials page can't tell whether the account has its Play Console permissions — that's checked by the first submit (`verify.md` → test build).

Also needed for the first submit, outside EAS: the **app in Play Console**, and **the first `.aab` uploaded by hand** (*Test and release → Testing → Internal testing → Create new release*) — Google's API can't make the first upload. While the app has never been published, submits use `releaseStatus: "draft"` (`eas.md`).
