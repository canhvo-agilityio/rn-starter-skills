# Release features

Only for what the app uses (`features` in the inventory). Each needs something store builds don't get by default — and works in development, so a missing piece shows up only in the hands of testers or users. Fingerprints are the **upload key** and the **Play app signing key** (`credentials-android.md` → Fingerprints); register both wherever a service asks.

| Feature | Detected by | Store builds need | If missing | Check |
|---|---|---|---|---|
| **Push notifications** | `expo-notifications`, `@react-native-firebase/messaging`, OneSignal | iOS: the Push capability on the App ID — EAS adds it from the `aps-environment` entitlement that `expo-notifications` sets — and the **APNs key** at whoever sends: on EAS for Expo's push service (`credentials-ios.md` → Push), else with the backend or Firebase. Android: `google-services.json` in the build (`android.googleServicesFile`) and an **FCM V1 service account key** at the sender (on EAS: `eas credentials -p android` → *FCM V1*) | no push token (capability) / pushes never arrive (key) | only on a real device: get the Expo push token, send one with `curl -H 'Content-Type: application/json' -d '{"to":"<token>","title":"test"}' https://exp.host/--/api/v2/push/send`, the dev confirms it arrived. No device → "push: not verified" |
| **Sign in with Apple** | `expo-apple-authentication`, `ios.usesAppleSignIn` | `ios.usesAppleSignIn: true` (adds the capability; EAS syncs it to the App ID). The App Store requires it when the app offers other third-party sign-ins (Google, Facebook) | sign-in sheet errors | sign in on a device with the TestFlight build |
| **Google Sign-In** | `@react-native-google-signin/google-signin`, `expo-auth-session` with Google | OAuth client ids for the release: iOS client for the bundle id (+ its reversed client id as a URL scheme in the config plugin); Android client(s) with the **SHA-1 of both** keys | works in development, fails in builds from TestFlight / Play ("DEVELOPER_ERROR" on Android) | sign in on the store build |
| **Domain links** (Universal Links / App Links) | `ios.associatedDomains`, Android `intentFilters` with `autoVerify` | `apple-app-site-association` on the domain with `<TEAMID>.<bundle id>`; `assetlinks.json` with the package and the **SHA-256 of both** keys — both at `https://<domain>/.well-known/` | links open the browser | open a link on a device; Android: `adb shell pm get-app-links <package>` shows `verified` |
| **Maps** | `react-native-maps` (Google provider), `@rnmapbox/maps` | a production API key restricted to the package + **SHA-1 of both** keys (Android) and the bundle id (iOS), as an EAS environment variable read by the config plugin; Mapbox: the download token as a `secret` EAS variable | grey map tiles | open the map screen on the store build |
| **Firebase / Analytics / Crashlytics** | `@react-native-firebase/*`, `googleServicesFile` | `google-services.json` / `GoogleService-Info.plist` **for the right environment** (production config in `production`). They're config, not secrets: commit them, or keep them out of git and pass them as `file` EAS variables | production events in the dev project, or nothing | Firebase console → DebugView / Crashlytics for a test event |
| **Sentry** | `@sentry/react-native` | `SENTRY_AUTH_TOKEN` as a `secret` EAS variable (source maps uploaded at build and on each OTA update), org and project in the plugin config | unreadable minified stack traces | trigger a test error in the store build, see it symbolicated in Sentry |
| **Permissions** | camera, location, photos, contacts, microphone, tracking modules | every iOS usage string the app needs, in the module's config plugin options or `ios.infoPlist` (`NSCameraUsageDescription`, …), written for users ("Coffee Shop uses your location to find nearby stores"), not left at the library's default | App Store rejection; a crash when the permission is requested | read `Info.plist` of the simulator build (`plutil -p <App>.app/Info.plist`) for each key |

Values that are secrets (Sentry token, Mapbox download token) go to EAS as `secret` variables, typed by the dev (`eas env:set … --visibility secret` in their terminal) — never in the chat. Public values (OAuth client ids, API keys restricted by app id) can be set by you.

Record each feature, what was set up and what still needs a device check in `docs/release-plan.md` → Release features.
