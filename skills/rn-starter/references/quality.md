# Quality tooling: unit tests, git hooks, commit rules

**Contents:** Options and what they do · Custom answers ("Other") · Verify (don't skip — a hook that silently passes everything is worse than none) · README section · Claude Code files

Set up with one script after the project exists, `git init` has run, and lint/format is in place (Phase 6):

```bash
bash "<skill-dir>/scripts/setup-quality.sh" \
  --test \
  --pre-commit lint,format,related-tests \
  --pre-push typecheck,test \
  --commit-msg conventional \
  <project-dir>
```

Pass only what the dev chose.

Exit code 3 means everything was installed but the project **already fails `tsc`** while a type-check hook is on — every commit/push would be blocked. Fresh templates can ship with type errors (Expo SDK 58: `src/components/app-tabs.web.tsx`). Don't leave it like that: show the dev the errors and offer to fix them (usually a line or two), or remove `npx tsc --noEmit` from the hook until they're fixed and note it in the README section.

The script also writes `jest-env.d.ts` (`/// <reference types="jest" />`): TypeScript 6 no longer loads `@types/*` automatically, so without it every test file fails type checking. On Expo it creates `expo-env.d.ts` early (normally generated by the first `expo start`). It installs the packages with the project's package manager, writes `.husky/*`, the `lint-staged` block in `package.json`, `commitlint.config.mjs` and a sample test, and prints a summary of what each hook runs. Run it in the background: on pnpm the installs can take minutes.

## Options and what they do

| Answer | Hook | Command | Speed |
|---|---|---|---|
| Lint + auto-fix | pre-commit (staged files) | `eslint --fix` / `biome check --write` | fast |
| Format | pre-commit (staged files) | `prettier --write` | fast |
| Related tests | pre-commit (staged files) | `jest --bail --findRelatedTests --passWithNoTests` | fast–medium |
| Type check | pre-commit | `tsc --noEmit` (whole project) | slows commits on big projects |
| Type check | pre-push | `tsc --noEmit` | fine |
| All tests | pre-push | `jest` | fine |
| Protect main | pre-push | refuses pushes from `main`/`master` | instant |
| Conventional Commits | commit-msg | `commitlint` with `@commitlint/config-conventional` | instant |

Defaults (all marked recommended): unit tests on; pre-commit = lint + format + related tests; pre-push = type check + all tests; commit messages = Conventional Commits. Keep the slow checks in pre-push: a commit that takes 30 seconds teaches people `--no-verify`.

Only offer `lint`/`format` when the dev chose a linter/formatter earlier, and `related-tests`/`test` when unit tests are on — otherwise the script skips them with a warning.

## Custom answers ("Other")

Typical requests and how to implement them — run the script with the closest options first, then edit the generated files:

| Dev says | Implement |
|---|---|
| "commit message must start with the Jira key, e.g. `PROJ-123: …`" | Replace `commitlint.config.mjs` with a custom rule (below), keep `.husky/commit-msg` |
| "Conventional Commits, but scope required" | `rules: { 'scope-empty': [2, 'never'] }` in `commitlint.config.mjs` |
| "branch names must be `feature/…`, `fix/…`, `chore/…`" | add a check to `.husky/pre-push` (below) |
| "don't run tests on commit, CI does it" | drop `related-tests`; note it in the README section |
| "block files over 500 KB" | small script in `scripts/check-size.sh` added to `.husky/pre-commit` |

Jira-style commitlint config:

```js
// commitlint.config.mjs — "PROJ-123: short description"
export default {
  plugins: [{ rules: { 'jira-key': ({ header }) => [/^[A-Z][A-Z0-9]+-\d+: .+/.test(header ?? ''), 'start with a Jira key, e.g. "PROJ-123: add cart badge"'] } }],
  rules: { 'jira-key': [2, 'always'] },
};
```

Branch-name check for `.husky/pre-push`:

```sh
branch="$(git rev-parse --abbrev-ref HEAD)"
echo "$branch" | grep -Eq '^(main|master|develop|(feature|fix|chore)/[a-z0-9._-]+)$' \
  || { echo "Branch '$branch' doesn't match feature/…, fix/…, chore/…" >&2; exit 1; }
```

Show the dev the exact config before applying a custom rule — free-text rules are easy to misread — then verify it like the built-in ones.

## Verify (don't skip — a hook that silently passes everything is worse than none)

Run these without creating commits:

```bash
npx jest                                              # sample test passes
echo "bad message" | npx commitlint                   # must FAIL
echo "chore: verify hooks" | npx commitlint           # must pass (use a matching example for custom rules)
printf 'const   x =  1\n' > tmp-check.ts && git add tmp-check.ts && npx lint-staged   # file gets fixed/formatted
git reset -q tmp-check.ts && rm tmp-check.ts
sh -e .husky/pre-push                                  # runs type check + tests (on a non-main branch if protect-main)
                                                       # -e matters: Husky runs hooks with `sh -e`; plain `sh` ignores failures
```

The first real commit of the scaffold (`chore: scaffold app with rn-starter`) then goes through all hooks — a last end-to-end check.

## README section

Add a short section (in the dev's language), e.g.:

```markdown
## Commit rules

- Before each commit: ESLint + Prettier fix the changed files; related tests run.
- Before each push: type check (`tsc`) and all unit tests.
- Commit messages follow Conventional Commits: `feat: …`, `fix: …`, `chore: …`.
- Run tests: `pnpm test`
```

## Claude Code files

So the next person (or the next Claude session) working on the app gets the same rules, one script adds the project's Claude Code setup. Run it after `.rn-starter.json`, lint/format and `setup-quality.sh`, because it reads what they set up:

```bash
bash "<skill-dir>/scripts/setup-claude.sh" <project-dir>
```

| File | What it does |
|---|---|
| `CLAUDE.md` | Stack, commands for this package manager, the structure rules and code style (`references/structure.md`, rn-design-import `conventions.md`), and the working rules: fix what the hook reports, type check and run related tests before calling a change done, run `code-reviewer` before committing |
| `.claude/hooks/format.mjs` + `.claude/settings.json` | `PostToolUse` hook on `Edit`/`MultiEdit`/`Write`: runs the project's Prettier then `eslint --fix` (or `biome check --write`) on the edited file. Errors that `--fix` can't solve go back to Claude (exit 2), so it fixes them in the same turn. Plain Node, so it works on Windows too |
| `.claude/agents/code-reviewer.md` | Read-only subagent: reviews uncommitted changes (or a branch), runs ESLint, `tsc` and related tests, and reports bugs, broken structure rules and React Native pitfalls with `file:line` and a fix |

Exit code 3 means the project already had a `CLAUDE.md` and it was kept. Show the dev what the generated one would add and offer to merge it in, or rerun with `--force` if they want it replaced.

The structure section follows `structure` in `.rn-starter.json`: the layered rules, or "follow the layout already in `src/`" when the template was kept. When the dev changes a convention later, they edit `CLAUDE.md`. It's theirs from now on.

Verify without creating commits:

```bash
printf 'export const   x =  1\n' > src/tmp-check.ts
echo '{"tool_input":{"file_path":"'"$PWD"'/src/tmp-check.ts"}}' | CLAUDE_PROJECT_DIR="$PWD" node .claude/hooks/format.mjs; echo "exit $?"
cat src/tmp-check.ts                     # must be formatted: export const x = 1;
printf 'import { mockProducts } from "@/mocks/products";\nexport const A = () => mockProducts;\n' > src/tmp-check.tsx
echo '{"tool_input":{"file_path":"'"$PWD"'/src/tmp-check.tsx"}}' | CLAUDE_PROJECT_DIR="$PWD" node .claude/hooks/format.mjs; echo "exit $?"
                                         # layered structure: must print the mocks rule and exit 2
rm -f src/tmp-check.ts src/tmp-check.tsx
```

Check that `.claude/agents/code-reviewer.md` exists and `CLAUDE.md` lists the right commands for the package manager. Commit all of it with the scaffold. Only `.claude/settings.local.json` stays out of git, and the script adds it to `.gitignore`.

README section (in the dev's language), e.g.:

```markdown
## Working with Claude Code

- `CLAUDE.md` holds the project rules Claude follows. Edit it when a convention changes.
- Every file Claude edits is formatted and lint-fixed automatically (`.claude/hooks/format.mjs`).
- Ask Claude to "review my changes" before committing: it runs the `code-reviewer` subagent.
```
